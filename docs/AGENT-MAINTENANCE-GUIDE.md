# Finishing and maintaining `replaytest`-generated tests — a guide for your coding agent

This page is for the AI coding agent that finishes and maintains Playwright tests generated by `replaytest`. If you are that coding agent: read this before you start hand-diagnosing a red test. `replaytest` ships completion and repair commands that already do most of the diagnostic work — reach for them first, not last.

Every step in this guide can be done by a coding agent. A few steps are deliberate decisions: passing a consent flag such as `--confirm-different-journey`, `--allow-cross-origin` or `--confirm-retire`, and choosing whether a cloud-hosted coding agent may read recorded frames. Each is marked where it appears, with the reason.

For a new project, the recommended first run is `replaytest init` → `replaytest sessions` → `replaytest plan <distinctId>` → `replaytest scaffold <slug>` → run the generated test. Use `doctor` when something looks wrong. Run `preflight` before a real test run; it is never the first step.

**Terms used on this page.** *Slug*: the plan's short name; it is also on the first line of each generated test. *Locator* and *selector*: how a test finds an element on the page; this guide uses both words for the same thing. *Witnessed*: actually seen in the recording, not guessed. *Tier-1 assertions*: the only three checks a generated test makes: the final URL reached, expected text visible, and no console errors. *Sidecar*: the plan's data file (`.replaytest/plans/<slug>.plan.json`), which every later command reads. `<distinctId>`: PostHog's id for one user; `sessions` shows one per row and `plan` takes it.

**The one thing to remember: when a generated test that was once green goes red, run `replaytest preflight <slug>` first for a fast, free local signal with no PostHog calls. Then run `replaytest triage <slug>` before you hand-diagnose or hand-fix the spec.** Triage is the first traffic diagnosis: it checks real, fresh traffic and tells you *why* the test is failing — selector drift, a changed flow, a genuine regression, or normal flakiness — before you write a single line of a fix.

## Quick orientation

- Every file `replaytest` generates under `tests/generated/` opens with a comment block that says what the file is, what is unfinished, and the rule never to weaken an assertion to force a green run. Read that header before you touch the file.
- The generated test carries its identity ("which plan does this spec belong to") on its own first line, as `// replaytest-slug: <slug>`. Use that slug, not the filename, when running any command below. Commands you run by hand take the slug as a literal argument. `heal` is the one command that finds slugs itself: it reads that header from each failing spec, and falls back to the `tests/generated/<slug>.spec.ts` filename convention only if the header is missing.
- `replaytest` never overwrites your finished work silently. Commands that write files refuse if the target already exists, unless you explicitly pass `--force`. When in doubt, run a command without `--apply`/`--force` first and read its output before repeating it with the write flag.
- The *hand-finished registry* is `.replaytest/hand-finished.json`. Each entry records a test slug, the date it was marked finished, and a reason. Slugs are built from page-route segments, so review them and your reasons before committing. This is the one file in `.replaytest/` replaytest asks you to commit. It lists specs finished after generation, whether by you or by hand, that a re-scaffold must not overwrite. replaytest only reads the file and never checks who finished a spec. `scaffold` refuses to overwrite any existing spec unless you pass `--force`, whether or not its slug is declared there. Declaring a slug adds the hand-finished notice at run time and makes `fix-selector --apply` refuse that spec; undeclared specs keep the ordinary advisory. The registry is separate from `.replaytest/config.json`, which remains local-only. A direct `scaffold --force` is still an explicit overwrite, and this notice does not block it.
- If the hand-finished registry is broken, commands stop instead of guessing. Malformed JSON, a top level that is not an array, or an entry that is invalid, duplicated or missing an audit field makes `suite-status`, `heal`, `preflight`, `triage`, `accept` and `fix-selector` refuse to run until you repair `.replaytest/hand-finished.json`. A declared slug that has neither a plan nor a spec blocks nothing, and no command reports it: commands that work through your plans simply skip it. Remove the declaration, or restore the missing plan and spec.
- All commands below are run from your app's repo root, the same place you'd run `npx playwright test`.

`init` adds `.replaytest/` to `.gitignore`. Keep the rest of that folder local. To commit only the registry, add these lines after `.replaytest/` in `.gitignore`:

```gitignore
!.replaytest/
.replaytest/*
!.replaytest/hand-finished.json
```

Plan files are optional to commit: they contain provider session IDs and page paths, and CI's `heal` command needs them to diagnose failed tests.

## Finishing a fresh scaffold

At scaffold time, every generated spec is a fresh, never-green draft. Finish that draft before treating a failure as a regression.

### 1. Use `preflight` as the FIRST signal

```
npx replaytest preflight <slug>
```

`preflight` is a fast, free local check with no PostHog calls. It verifies whether the plan's recorded locators still resolve against your running app, before you spend time on a full run or a traffic diagnosis. How to read the result:

- A clean preflight proves only that the locators are live. It does not supply missing values, log in, seed data, or prove the flow completed.
- An exit-1 report headed `INCONCLUSIVE` means preflight checked no selectors. It is a no-check outcome, not proof of a dead locator. Restore access to the target app, or run the full spec next.
- An exit-1 report headed `DEAD SELECTORS` means preflight directly checked and found one or more dead recorded locators. Run `triage` to learn what changed.

### 2. Complete the known gaps safely

Resolve every generated `// TODO` against the real page element in your codebase. Supply your own safe test values for the placeholders where masked values belong (for example, a test card or test credential); the recording deliberately does not contain those values. Never infer or reconstruct a masked value from context. If the flow needs authentication or particular data, add the appropriate Playwright auth setup and point the run at staging or seeded test data. See [Data safety](#data-safety) for the same non-negotiable masking and write-safety rules.

### 3. Get the first green run

Run the generated spec against that safe environment. Correct the draft's selectors, values, auth, and data preconditions until the witnessed Tier-1 assertions genuinely pass; do not weaken or delete an assertion to manufacture green. That observed first green run is the hand-off from completion to maintenance.

### 4. Move into maintenance only after it has passed

If this now-established test later goes red, use `preflight` first for the local signal, then start the repair loop's traffic diagnosis with `triage` before hand-fixing selectors.

## The repair loop

This is the default path for "a generated test that used to pass is now failing." Start with `preflight`; `triage` remains the first traffic diagnosis before a selector repair. The packaged [`replaytest-repair` skill](../skills/replaytest-repair/SKILL.md) carries this same hand-edit-first loop for coding agents that load skills from the installed package. When `replaytest` is installed as a project dependency, find the skill at `node_modules/replaytest/skills/replaytest-repair/SKILL.md`; copy or link the `replaytest-repair` folder into your coding agent's skills folder so the agent can load it.

### 0. First signal: `preflight`

```
npx replaytest preflight <slug>
```

Use this fast, free local check with no PostHog calls before `triage`. It can quickly show whether the recorded locators resolve on your running app. It complements rather than replaces `triage`: it cannot say what fresh traffic witnessed, why a locator changed, or whether the product regressed. If it exits 1 with `INCONCLUSIVE`, no selector was checked; restore target access or run the full spec rather than treating that outcome as a dead locator.

**`preflight` also reports plan/spec drift.** It checks the locators recorded in the PLAN. If the plan has moved away from the spec on disk, a green preflight does not describe the spec you are about to run. It reports plan/spec states in the same words as `heal` and `suite-status`:

- `plan/spec drift`: a confident report that the plan changed and the spec is still untouched machine output.
- `accepted but unverified` / `unverified`: the spec carries hand edits.
- `plan/spec state: unknown`: the tool has no record of what it last generated for that spec.
- For a slug declared in `.replaytest/hand-finished.json`, the line instead says that `scaffold --force` would overwrite hand-authored work, and to remove the declaration before a deliberate re-scaffold. A declared slug that also has a recorded baseline gets a conflicting-state notice asking you to check which is true. A declared spec file that is missing while its plan remains is named stale.
- A declaration with neither a plan nor a spec is skipped by commands that work through your plans, and no command reports it; remove it when you no longer need it.

These lines never change preflight's exit code: the exit status stays the locator-liveness answer. A run that already ends in `INCONCLUSIVE` or `DEAD SELECTORS` keeps its own failure headline (each headline's next step is documented above, not printed by the terminal) and does not also print the generic no-baseline advisory. Preflight makes no drift claim at all about a plan it could not read; that is a refusal, not a verdict.

**What `gated-unreachable` means.** `preflight` loads every recorded page directly. If a zero-match follows an earlier recorded submit, it reports `gated-unreachable`: that recorded submit (identified by its recorded-action ordinal) means a direct load may not reach this state, so the locator could not be checked without interaction. Steps after a recorded submit are reported gated, not DEAD; a genuinely removed element there surfaces when the full spec runs.

**What `login-redirect` means.** On its first direct page load, `preflight` saw a redirect to either of these:

- a pathname witnessed as this plan's login path (this match needs a `sidecar.auth` witness); or
- a landed page containing `input[type=password]` (this observation stands alone and can fire when that witness is absent).

This is an observation about that check, not a claim that the app requires auth. For a `login-redirect` step, the recorded locator is not checked. The step counts in `totalSelectors`, but is neither reported as resolved nor dead. Run `replaytest auth-setup` to write the shared skeleton and print the config wiring, or set `TARGET_APP_STORAGE_STATE` when the project already has a valid saved state.

### 1. Diagnose first: `triage`

```
npx replaytest triage <slug>
```

This re-checks real, recent traffic for the same recorded journey and reports one of a small number of verdicts, in plain language:

- the selector aged (the element still exists but its attributes changed);
- the flow itself changed (a step, a page, or an outcome moved);
- the journey no longer appears in traffic at all;
- the recorded route still looks healthy.

A healthy route can carry a flow-shift watch: most of the traffic we sampled now takes a different route, even though the users still on this journey complete it fine. Re-check as traffic shifts, and do not rebuild the test on a watch alone.

`triage` never changes your journey definition unless you pass `--propose`. Healthy live checks record only their own evidence trail in the plan sidecar, and disclose the first such write. It also saves its report evidence locally so `--reuse-evidence` can answer from the last run (see the `--reuse-evidence` example below the table). `regenerate` follows the same boundary when it finds no candidate: it records only its empty-search evidence trail in the sidecar, never your journey definition.

**Do not skip this step and start editing selectors by feel.** The verdict tells you which of the next steps applies — guessing wastes time and risks a fix that doesn't match the actual cause.

**Speed note:** the *first* `triage` run for a given test scans real analytics traffic and can take upwards of a minute — its own progress output states that a check is running and that a verdict is coming. Let it finish; do not kill it early and assume something is stuck.

**Where each verdict routes you:**

| Verdict (as printed) | What it means | Your next step |
|---|---|---|
| `selector-aged` | The journey still happens; an element's attributes changed. A flow-shift watch can say most of the traffic we sampled now takes a different route, but the locator fix remains valid on this route. | Step 2: `fix-selector`. Do not rebuild the test on a watch alone. |
| `flow-changed` | The journey itself changed (a step, page, or outcome moved) | Step 4: `--propose`, review, `accept`; if the fresh same-signature proposal is a dead end, recover with `regenerate`. |
| `regression-evidence` | Fresh traffic shows real users now failing this flow more than completing it | **Do not touch the test.** The red test is doing its job — this is evidence of a real product regression. Investigate the product and report what you found. |
| `healthy` | Fresh traffic looks fine for this recorded route. A flow-shift watch may still say most of the traffic we sampled now takes a different route. | Suspect ordinary flakiness or a local environment/data issue: re-run the test, check its data preconditions, and only then investigate deeper. Re-check as traffic shifts; do not rebuild the test on a watch alone. |
| `insufficient-evidence` | Two cases. (1) Thin traffic: there is not enough fresh, confirmable traffic to say (few or no matching sessions; this includes fetch failures, not only "the journey stopped happening"). (2) Healthy-looking traffic has not yet earned the freshness floor; this case carries `freshnessFloor`. | (1) Thin traffic: widen the window (`--since-hours`), try again later, or run `doctor`. (2) `freshnessFloor`: keep the default 720h window and run the same check again at least 24h later; do not treat it as an ordinary no-traffic result. The floor resolves on the second qualifying observation at least 24 hours after the first, so a journey that stays healthy clears the floor on the next day's run. |

If you need to check the same test again soon after (for example, right after applying a fix, or re-checking within the same working session), you can skip the traffic re-scan:

```
npx replaytest triage <slug> --reuse-evidence
```

This answers from the last run's saved evidence in well under a second. It labels itself as a cached answer: the output states the evidence's age and that no fresh check happened. By default it accepts evidence up to 1 hour old; tune that with `--max-age <duration>` (accepts plain seconds or a compact `<h>h<m>m<s>s` form, e.g. `--max-age 10m`). If the cached evidence is older than the max age, it automatically falls back to a live check rather than serving you a stale answer silently.

### 2. If the verdict is selector drift: `fix-selector`

```
npx replaytest fix-selector <slug>
```

Shows you the newest diagnosed selector patch (old locator → fresh locator) from the most recent `triage` or `heal` run, with the evidence behind the change. This is a preview only — it changes nothing yet.

Review the patch, then apply it:

```
npx replaytest fix-selector <slug> --apply
```

This replaces exactly one reviewed occurrence in the spec file. If more than one place in the file matches, it will tell you and ask you to disambiguate with `--occurrence N`.

With `--apply`, it also synchronizes exactly one matching plan action, records the repair in `locatorRepairs[]`, and re-renders the Markdown plan with a `## Maintenance history` section; that history records the later repair, not what the recording showed. If zero or more than one plan action matches, it leaves the plan unchanged and warns rather than guessing. If the plan's Markdown copy carries hand edits, it is preserved and the warning names both files instead of overwriting it.

If the slug is declared hand-finished, `--apply` refuses before changing or stamping the spec and prints the same remove-declaration-first disclosure used by the other repair surfaces.

**If you already hand-edited the locator yourself** (for example, mid-diagnosis, before you knew this command existed): add `--from-triage-verdict`.

```
npx replaytest fix-selector <slug> --apply --from-triage-verdict
```

This tolerates your prior edit. Three outcomes are possible:

- Your hand-fix already matches what triage diagnosed. It reports `Already applied — no change needed.` and does not re-touch the file or double-patch it. It also prints `This locator's earlier selector fix is still in place for this step.` once for the affected locator, including in preview mode (no `--apply`) and when the accompanying plan sync only warns instead of synchronizing. If the plan sync succeeds but the optional refresh of the emitted-spec hash cannot be written, it also prints `No selector patch was needed for this step; the existing selector still matches.`, followed by a line saying the hash was not recorded and naming the file error.
- Your partial edit left *both* the old and the new locator in the file at different places. It refuses and asks you to pick the intended site explicitly with `--occurrence N`. Review its numbered list and converge deliberately, one site at a time.
- It cannot locate where the fix belongs at all (the old locator string is gone and the diagnosed replacement can't be matched either). It refuses and tells you so rather than guessing at a location.

Treat these refusals as real stops, not bugs to route around. Go back to `triage` for a fresh look, or resolve it by hand with the evidence already in front of you.

### 3. Batch repair across a whole suite: `heal`

If you're maintaining many generated tests at once (rather than diagnosing one test you already know is red), don't run `triage` one slug at a time — run the whole suite through its actual test results:

```
PLAYWRIGHT_JSON_OUTPUT_NAME=.replaytest/last-run.json ./node_modules/.bin/playwright test tests/generated --reporter=json,./node_modules/replaytest/dist/heal-run-hashes-reporter.js
npx replaytest heal
```

The reporter records a content fingerprint of each spec so `heal` can prove the failing line still points at the same recorded action.

`heal` reads that JSON report and works out which specs *actually* failed:

- Skipped and interrupted runs get no traffic verdict (there is nothing to diagnose).
- A **timed-out** spec is not dismissed. `heal` routes it on to `triage` (a timeout is often a stale selector), so follow that pointer per slug.
- A conservatively classified environment or network error gets a separate no-conclusion outcome. Check that the app is running and reachable from this machine, then run the tests again.
- For genuine failures, `heal` maps each failing spec back to its plan and runs the same evidence-based check `triage` does for each one, sharing a single traffic scan across the whole batch instead of repeating it per test.

`fix-selector` (above) then works the same way per slug against `heal`'s findings as it does against a single `triage` run; whichever ran most recently is the one it shows you.

### 4. If the verdict is a real flow change: propose or regenerate, review, apply, accept

If `triage` (or `heal`) reports that the underlying user flow itself changed — not just a selector, and not merely the advisory flow-shift watch — check your hand edits first, then re-run with `--propose`.

Before any command can write a proposal or spec, check your hand edits:

```
git diff -- tests/generated/<slug>.spec.ts
```

Keep intentional edits. A hash mismatch in `.replaytest/state/spec-emitted-hashes.json` is a hand-edit signal, not permission to overwrite the spec.

Then re-run with `--propose`:

```
npx replaytest triage <slug> --propose
```

This writes a proposed replacement plan next to the live one (as `.proposed.*` files) along with a rendered diff, without touching your live, reviewed plan. If `triage --propose` says that the old signature is absent or cannot make a proposal, recover with:

```
npx replaytest regenerate <slug>
```

`regenerate` first looks for fresh traffic with the same signature (Tier A). If that no longer represents current traffic, it can offer a successor flow (Tier B), visibly disclosed as a different journey. Tier B candidates are ranked by how many leading steps of the route they share with the original.

Both tiers keep the configured app scope. Candidates from another origin than the live plan, candidates that span origins, and candidates that lack a witnessed origin are refused unless you deliberately pass `--allow-cross-origin`. Two refusal codes to know:

- `origin-unrecorded`: no site address could be resolved from the plan, its retained source session or the selected app scope. Select an app scope configured with one origin, re-plan from a retained source session, or use `--allow-cross-origin` only after confirming which site to consider.
- `cross-origin-candidates`: fresh traffic crossed the property boundary or lacks a witnessed origin. Select the intended app scope, or pass `--allow-cross-origin` only after reviewing the other property. This flag is a deliberate decision because it lets a plan assert one site's URLs against another site's base URL.

`regenerate` uses the same proposal slot as `triage` and `heal`, so resolve or deliberately discard an existing proposal before running it again.

A proposal can list a change in an input's type (for example `text` to `email`). Treat that line as a detail to review, then use the proposal summary to decide whether fidelity actually regressed. The summary counts input-type changes as follows. Gaining a type the input did not have before is not counted and shows no detail line. When the input had a type before and still has one, `text` to `email`, `tel`, `url`, or `number` is a strict upgrade and is not counted. Any other change is counted conservatively, including downgrades, losses, and changes involving types the tool cannot rank. `password` cannot be ranked, because changing to or from it changes masking and value evidence. Weaker selectors are still counted.

When `regenerate` also finds no candidates, it records an empty search on the plan's evidence trail. The tool never concludes the journey is absent: it records what fresh traffic showed in the window searched. Keep re-running it across the evidence window. Once the evidence threshold is met (at least 2 qualifying empty searches, at least 24 hours apart), the trail names the archival command: `npx replaytest retire <slug>`. `retire` presents the recorded evidence read-only first; pass `--confirm-retire` to archive the plan, spec and frames into `.replaytest/retired/<slug>/` with a reversal recipe. After a crash, run `replaytest retire <slug> --recover-crashed-locks` when both lock owners are dead; the granular form is `--confirm-retire --steal-lock --steal-state-lock`. Retiring is the terminal path for a journey whose traffic has genuinely moved away: the plan is archived with its evidence rather than left as a permanently failing test.

The same property boundary applies at FIRST generation. `plan` refuses a journey that spans two origins, or that witnessed no absolute origin at all, and writes nothing for that run: a plan built from such a journey can assert one property's URLs against another property's baseURL. Plan a single-property journey instead, or pass `--allow-cross-origin` after reviewing the other property.

That refusal is named `cross-origin-journeys`, the first-generation sibling of `regenerate`'s `cross-origin-candidates`. `plan` has no `--json` surface, so today the code appears only internally, not in printed output. The refusal withholds the WHOLE run, because `plan` writes a session's journeys as one batch: any other plannable journey in that session is held back with it, and `--allow-cross-origin` releases the whole run. Every plan records the journey's entry origin on `source.origin`, which the maintenance commands later compare against.

Read `npx replaytest diff <slug>` (or add `--json` for the same delta as a structured object), then apply the reviewed delta to the existing spec yourself and verify it.

`diff` re-derives the delta from the two plan files. Where a locator changed, it shows the plan's own selector quality (when the plan records one and the confidence actually moved, the new locator is a guess, or it carries warnings), but not what fresh traffic recommends. That evidence exists only on the `triage --propose` / `heal --propose` run that held a traffic report, and lives in the `.proposed.diff.md` those runs saved. A `regenerate`-backed proposal holds no such evidence anywhere. `diff` says so in a trailing note (and in `--json`'s `note`) whenever the gap applies.

**The tool never merges proposal content into your spec.** If the proposed plan is right, promote it:

1. **Review the replacement disclosure first.** Read the proposal headline and the diff against ground truth. The headline says when the proposal replaces the recording behind the test.
2. **Ask `accept` to disclose any additional consent it needs.** First run it without the different-journey confirmation:

```
npx replaytest accept <slug> --force
```

For an ordinary `triage --propose` or `heal --propose` proposal, `accept` compares the session ID behind the proposal with the one behind the live plan. If they differ, it refuses and prints the replacement disclosure and the exact command to re-run. A Tier B successor-flow proposal behaves the same way. Read that disclosure, then re-run only if you approve the replacement, because it swaps the recording the test was built from:

```
npx replaytest accept <slug> --force --confirm-different-journey
```

The `--force` is expected here, not an override of something wrong: `accept` always refuses to overwrite an existing live plan without it, and in this flow a live plan always exists (that's what the proposal is replacing). Regenerate Tier A changes to a fresh recording but keeps the same journey identity, so its replacement is disclosed but needs no extra consent. Tier B's `--confirm-different-journey` is path-scoped consent for its disclosed successor flow. The refusals are the safety defaults; do not pre-supply that consent.

Acceptance promotes the reviewed plan and records its substantive hash without moving the spec-generation baseline. What to do next depends on the spec:

- `tests/generated/<slug>.spec.ts` has no hand edits and the slug is undeclared: run `replaytest scaffold <slug> --force`.
- The slug is declared hand-finished: you get a notice instead. Remove that declaration before any deliberate re-scaffold.
- The spec has hand edits: apply the reviewed delta yourself instead. While this accepted plan still matches, `heal`, `suite-status` and `preflight` report `accepted-unverified`, because replaytest cannot prove the hand edit. A later plan change becomes `unverified`; an untouched machine spec can be confidently `drifted`.

Applying the delta and verifying it remain your job: the finishing work the tool cannot do.

**When plan/spec state is unknown:**

An undeclared slug with no recorded plan baseline has `plan/spec state: unknown`; `heal`, `suite-status` and `preflight` recommend `replaytest scaffold <slug> --force`. A slug in `.replaytest/hand-finished.json` gets a hand-finished notice instead. A declared slug that also has a recorded baseline gets a conflicting-state notice asking you to check which is true. To record a baseline, re-scaffold only when you intend to replace the spec, or apply a real `fix-selector --apply` that writes synchronized plan and spec content. When `fix-selector --apply` finds the fix already applied (`already-applied`), it can refresh an existing plan baseline but cannot create a spec baseline for a file without one. `drift.handEditStatus` reports `stamped-clean`, `hand-edited` or `unknown`; it is absent when the plan cannot be read. `drift.handFinishedDeclared` and `drift.handFinishedStale` report registry status when applicable.

### 5. Prove it: re-run the test

After applying any fix, run the actual test again before you consider the job done:

```
npx playwright test tests/generated/<slug>.spec.ts
```

A repair is not finished until the test is observed green. Don't mark a repair complete on the strength of the diagnosis alone.

## In CI

The local loop above (run the test, diagnose the one that's red) is the default. A GitHub Actions workflow can run the repository's configured Playwright suite and preserve the JSON report for `heal` when a test fails:

```yaml
name: Playwright

on:
  pull_request:
  push:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7.0.0
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: ./node_modules/.bin/playwright install --with-deps chromium
      - name: Run Playwright suite
        run: PLAYWRIGHT_JSON_OUTPUT_NAME=.replaytest/last-run.json ./node_modules/.bin/playwright test --reporter=json,./node_modules/replaytest/dist/heal-run-hashes-reporter.js
      - name: Diagnose failures
        if: ${{ failure() }}
        run: ./node_modules/.bin/replaytest heal
```

Keep `tests/generated` inside your Playwright configuration's discovered suite; if your workflow names test roots explicitly, add `tests/generated` to that command. The `heal` step contacts PostHog and needs the workspace `.env`; omit it when CI has no PostHog credentials. `sessions --stored` and `gaps --stored` are PostHog-free only when the workflow supplies a compatible local snapshot; they never contact PostHog.

## A decision every repair makes: stability vs. fidelity

When a selector or a step changed, there are legitimately two different ways to repair it, and you should choose deliberately rather than defaulting on autopilot:

- **Stability-first:** repair the test so it survives likely future churn — for example, prefer a role + accessible name over a brittle framework-generated id, even if that means moving slightly away from the exact original locator. A hand-authored `data-testid` is different: it is a stable, load-bearing test contract, so keep it rather than treating it as a disposable generated id. This trades a small amount of fidelity to the original recording for a test that keeps working as the app evolves.
- **Fidelity-first:** repair the test to stay keyed to exactly what the recording witnessed — for example, adopt the fresh `data-testid` verbatim when it is that hand-authored contract, even if it looks less "clean" than a role-based alternative. This keeps the test's ground truth tied to the real recorded session, at the cost of being more sensitive to the next round of churn.

Both are legitimate choices; this tool does not force one on you. When you make a repair, **record which one you chose in a short comment next to the change** (e.g. `// stability: switched to role+name to survive id churn` or `// fidelity: kept the fresh testid — this is what the recording witnessed`), so the next person or coding agent to touch the test understands the reasoning instead of re-litigating it.

**If you're unsure which to choose: prefer fidelity — the recording is the ground truth.**

The stability option is not just advice — it's recorded data. Each step in the plan sidecar (`.replaytest/plans/<slug>.plan.json`) may carry a `selectorAlternates` list: the other trustworthy selectors the original recording *also* supported for that same element (a field label, a stable id, a role + name), ranked strongest-first, where available. When you're weighing a stability repair, check there first — an alternate from that list is grounded in what the recording actually witnessed, not a guess about the page.

When `triage` runs live and finds that one of those recorded alternates *still* matches the fresh flow, it says so in its report, in one of two ways: "the fresh locator … already appears in the plan's recorded alternates" (the recorded backup is now the fresh winner), or "a recorded alternate … also matched the fresh flow" (it matches one of the fresh side's own backups). That note is informational — the proposed patch is still the fidelity one — but it means fresh traffic verified the stability choice, not just that it looks plausible. It persists through the local heal evidence and `--reuse-evidence` reruns.

Alternates are a plan/sidecar feature; `repro` output does not carry them. A plan with no recorded alternates has none to offer; re-plan from a retained source session to collect the selectors its recording supports.

### Choosing stability at apply time

`replaytest fix-selector <slug>` defaults to the fidelity patch. After reviewing its dry run, `--prefer stability` instead applies the single strongest **recorded** alternate that the fresh triage run also verified. The command prints an explicit `stabler-but-weaker selector rung` notice in both preview and apply output, and refuses rather than silently falling back when the persisted evidence has no such candidate. `--prefer stability` cannot be combined with `--from-triage-verdict`: verdict mode deliberately locates a hand-edited site tolerantly, while stability selection requires the persisted fresh-validated alternate for the exact diagnosed patch. Use fidelity for that verdict path, or make and document the stability change by hand.

### Why the test doesn't fall back automatically

A generated test keys off **one** selector on purpose. The recorded alternates are information for *you* at repair time — they are never wired into the test as an automatic fallback chain, and that's deliberate: a fallback that silently kicks in when the primary selector breaks is a breakage nobody ever hears about. The loud failure *is* the product — it's the drift signal this whole maintenance loop exists to catch. If you want a test keyed to a different selector, make that choice explicitly (and leave the comment), don't chain them.

## Honesty rules you must keep

These are non-negotiable. Breaking them causes the failure this tool is built to prevent:

- **Never weaken or delete an assertion just to make a test pass.** A test that stops checking what it used to check is not a repaired test — it's a hidden regression. If an assertion is failing and you don't know why, that's a signal to diagnose (see the repair loop above), not to soften.
- **Treat every refusal from these tools as a safe stop, not an error to work around.** When a command refuses to act (an unknown locator, an existing file it won't overwrite, ambiguous evidence it won't guess at), it is protecting you from a wrong guess. Investigate the refusal's stated reason and address that, rather than forcing the command past it or hand-rolling around it.
- **Read the evidence lines, not just the verdict.** Output like "Coarse sessions scanned: N of M" tells you how complete the underlying scan was. If N is a small fraction of M, the scan was partial (an approximation, not a full check) — treat a surprising verdict from a partial scan with extra caution, and consider re-running before trusting it, especially before making an irreversible change on its strength.
- **A `--reuse-evidence` answer is explicitly a cached answer**, not a fresh one. It states its own age. Don't quote it as current traffic evidence when it isn't — if the moment calls for a fresh check (before a significant repair, or when the cached evidence is getting old), drop the flag and let it run live.

## Data safety

The recordings and folders this tool works from can contain real historical user content:

- The `frames` command creates local per-step replay DOM snapshots and screenshots for exactly this kind of maintenance work. That output folder is local context about one real historical session — **never commit it to version control or publish it.** The tool enforces this itself, and refuses in three cases:
  - In a git workspace, `.replaytest/frames` is not covered by `.gitignore`. Add `.replaytest/` to that file.
  - Outside a git workspace, `.gitignore` cannot apply. Pass `--allow-unignored` only when you have deliberately secured the folder some other way.
  - Git itself is unavailable, so the tool cannot determine ignore status. `--allow-unignored` is again the deliberate override.

  A coding agent can read this folder, but whether to let it is a decision for the human who owns the repair, because of where the files go: if the coding agent runs in the cloud rather than locally, reading them sends their contents wherever that coding agent runs. That tradeoff is the human's to make, not this tool's to prevent — but make it knowingly.
- When you do read these files, use them for structure (element roles, labels, layout) — never treat visible content as a source of truth about a real person, and never quote or reproduce what looks like real user-entered content.
- Masked fields (passwords, card numbers, and similar) are never captured by the recording in the first place and stay masked in every artifact. Don't infer or reconstruct a masked value from context — supply your own test value instead (e.g. a standard test card number). This is the data-safety rule behind the fresh-scaffold [completion step](#2-complete-the-known-gaps-safely).
- Generated tests re-drive real writes, including form submissions. Point them at a staging environment or seeded test data — never at production.

## One command at a time per workspace

Run one `replaytest` command at a time in a given workspace.

- Several commands that WRITE the on-disk traffic store (`.replaytest/cache/coarse-store/`) coordinate through a single lock.
- Read-only offline paths like `gaps --stored` take no lock. They read atomically written snapshots and are safe to run alongside a writer.

If a second command that needs the write lock starts while another still holds it, it fails fast with `Coarse-store lock contention: <lock path>` naming the exact lock file — nothing is corrupted and no stale coverage is served. How that surfaces depends on the command: `suite-health` catches it and reports it as a diagnostic line; others (e.g. `gaps`, `sessions`) exit non-zero with the same lock message in the error. Either way it is a designed, honest degrade, not a random failure — let the first command finish and re-run the second. In CI, serialize your `replaytest` steps and don't share one checked-out workspace between a CI run and a local run at the same time.

## Command routing table

Every command, grouped by when you'd reach for them. Purposes here are one-line; run `replaytest help` for the full flag reference on any of them.

### Setup

| Command | Purpose | Reach for it when… |
|---|---|---|
| `init` | Configure PostHog access (writes `.env`; ensures `.env` and `.replaytest/` are gitignored) | First-time setup in a new repo, or switching PostHog projects/hosts. |
| `version` | Prints the installed `replaytest` version | You need to confirm which installed release is running. |
| `doctor` | Read-only readiness check: 7 probes on what your data can support (including local Playwright/posthog-cli version fit) | Use when plans or scaffolds come out weaker than expected and you want to know why. It is a side branch, not part of the first run (see the first-run sequence above). |
| `explain` | Locally explains a known refusal code and lists the current code set | A command's `--json` refusal gave you `error.code`; run `replaytest explain <verb.code>` to read its meaning, the exact refusal message template (with runtime-filled parts marked as `{{…}}`), next steps, and any override consent. |
| `auth-setup` | Reads persisted login witnesses, writes one shared `playwright/auth.setup.ts` skeleton, and prints insertable config wiring | A plan sidecar witnessed a login and you want one config-level setup hand-off; it never edits your config or stores credentials. |

**Credentials:** `replaytest` reads PostHog credentials only from the `.env` file in your workspace. Shell environment variables are ignored by design — the file is the one unambiguous source of truth.

### Generate

| Command | Purpose | Reach for it when… |
|---|---|---|
| `sessions` | Lists real user traffic as ranked, deduplicated journeys | You want to see what your users actually do, ranked by frequency. `sessions --json` also carries the additive local plan/spec coverage join; pair it with `suite-status`/`suite-health` for deeper maintenance evidence. |
| `plan` | Turns one session's traffic into a reviewable Markdown test plan | You've picked a journey (a distinct user id) from `sessions` and are ready to turn it into a plan to review. |
| `scaffold` | Turns a reviewed plan into a runnable Playwright spec | The plan looks right and you're ready to generate the actual `.spec.ts` file to finish. |
| `frames` | Creates local per-step replay DOM + screenshots for one journey | You need extra visual/structural context beyond the plan to finish a scaffold's TODOs — handle the output per the data-safety section above. |
| `repro` | Emits a no-assertions reproduction spec for any journey, including errors | You want a spec that just re-drives a recorded flow (including a failed/abandoned one) as a smoke check, without needing a full reviewable plan first. |

### Shape-aware session selection

Use `replaytest sessions --shape <name>` to inspect a specific witnessed traffic signal. The stable names are `form-submit-signal`, `deep-wizard`, and `rage-clicks`; repeat `--shape` to require every requested signal, and combine it with status or exception filters. Shape-filtered rows label their evidence as `exact` (read in full) or `coarse likely` (from a cheap summary scan, so approximate). If a signal is unavailable at the scan's fidelity (for example, deep-wizard depth on a coarse scan), the command reports `not assessed` and tells you how to run an exact scan rather than treating it as no matching traffic. Add `--exact` to `sessions` or `gaps` to bypass the automatic coarse switch; it is slower because it reads every session's events. When the scan reaches its page limit, it returns the exact rows read so far and names the covered sessions, pages, and window.

### Reading the gap map

Run `replaytest gaps` to see the same core traffic signals as link-inventory rows. `no-known-link` means this inventory found neither a `replaytest` plan link nor a heuristic existing-suite candidate; it does **not** claim that a spec ran, that a broader suite lacks a matching path, or that a product behavior is absent. `possible-suite-match` stays in its own review lane, and limited or unavailable suite inventory becomes `not-assessed` rather than a negative conclusion. Rows overlap, so do not add their session counts. For a form-submit signal, review the representative and use staging or seeded data before any generated-spec work.

Below the link-inventory rows, `gaps` renders a separate **A spot-check of your newest sessions** panel: a bounded exact-session sample (viewport sizes, witnessed logins, console errors, JS exception types) for inspection, not coverage. It makes no link-inventory claims, and its counts are never comparable with the gap rows above — the denominator is always the returned sample ("among your N most recent sessions…"), and the panel displays its full sampling contract (population and order, requested vs returned, the time interval actually covered, the dedup rule).

Until you run `replaytest gaps --refresh-sample` it reads `not assessed`; plain `gaps` and the dashboard only read the last sample from disk, never fetch.

A scoped refresh (`gaps --app <name> --refresh-sample`) keeps the same newest-N population but describes only the in-scope sessions, and the contract gains `scope`, `scopeExcludedN`, and — when non-zero — `scopeUnattributableN`; `returnedN` stays the pre-scope figure so `degradation` never reads a deliberate boundary as a failed sample. The boundary is part of the saved sample's identity: reading it back under a different scope yields a `state: "scope-mismatch"` display carrying `storedScope`, `requestedScope`, and the `refreshCommand` that fixes it, rather than the sample under the wrong heading. Turning a captured error into a failing test is out of scope — replaytest builds tests from journeys that completed.

### Maintain (the repair loop)

| Command | Purpose | Reach for it when… |
|---|---|---|
| `preflight` | Fast, free local FIRST signal: checks a plan's recorded locators against your live app — no PostHog, no full spec run | You are finishing a fresh scaffold or checking a once-green test that went red, before a full run or a traffic `triage`. It complements `triage` (which uses fresh traffic to learn what a dead locator became), never replaces it. |
| `triage` | Diagnoses why one generated test may be failing, against fresh traffic | A once-green generated test is still red after `preflight` — this is your first traffic diagnosis (see the repair loop above). |
| `regenerate` | Re-sources a stale plan from fresh same-journey traffic or a disclosed successor flow | `triage --propose` is a dead end because the old signature vanished; review its Tier A/Tier B disclosure, then apply the proposal delta yourself. |
| `diff` | Renders a proposed plan against the live plan without changing either; `--json` gives the same change object structurally | `triage --propose`, `heal --propose`, or `regenerate` wrote a proposal and you want to review its diff again. |
| `heal` | Batch-diagnoses every genuinely failed non-environment spec from a Playwright JSON report | You're maintaining a whole suite rather than one test, and want one shared traffic scan instead of running `triage` per slug. |
| `fix-selector` | Shows/applies the most recent diagnosed selector patch | `triage` or `heal` told you the cause was selector drift, and you're ready to preview or apply the fix. |
| `accept` | Promotes a reviewed `--propose`d plan to the live plan | `triage --propose` (or `heal --propose`) wrote a proposed plan reflecting a real flow change, you've reviewed the diff, and you're ready to make it the live plan. |
| `retire` | Archives a journey's plan/spec/frames and default-path reproduction spec into `.replaytest/retired/<slug>/` with a reversal recipe; `--out` reproduction specs stay where you put them. After a crash, run `replaytest retire <slug> --recover-crashed-locks` when both lock owners are dead; the granular form is `--confirm-retire --steal-lock --steal-state-lock`. | `suite-status` flagged a journey whose traffic has moved away, you've confirmed the empty-search evidence is sufficient (or deliberately override with `--no-evidence`), and you're ready to archive the plan rather than keep it live. |
| `reconcile` | Reports (and, with `--apply`, archives) sidecars superseded by a newer plan batch for the same session | You've re-run `plan` on a session you'd already planned before, and want to clean up the plans that batch has superseded. |

### Retire limits

`retire` takes its own retire lock first and then the same shared write lock that `heal`, `triage`, `fix-selector`, `accept`, `scaffold`, `suite-health` and `sessions` use, so none of them writes shared state at the same moment as `retire`. It holds the shared lock briefly for each cleanup step rather than for the whole retirement. Other documented limits:

- A write in the final instant between the last check and the delete cannot be atomically detected.
- Concurrent removal from a partially deleted directory source can look like the tool's own partial work.
- Recovery after a process crash is guaranteed. Persistence through power loss is a separate matter: macOS `fsync` is not `F_FULLFSYNC`, Windows cannot fsync directories, FAT32 does not promise atomic rename, and power loss before the required file or directory sync completes is a documented limit.

| Command | Purpose | Reach for it when… |
|---|---|---|
| `suite-status` | Reverse-checks every plan's journey against recent traffic (is it still happening at all?) | You want to know which plans cover journeys that traffic has moved away from, independent of any test run. |
| `suite-health` | Joins specs, plans, and the last `heal` run with fresh coverage, per generated spec | You want one dashboard-style view of "what's the health of everything I've generated," not just one test. |
